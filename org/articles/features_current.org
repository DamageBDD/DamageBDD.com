* How to interpret the status

An inspected API establishes that an implementation is present in the named
snapshot. A static patch check establishes that the change applied to its
baseline. A recorded live result establishes the particular scenarios on the
identified deployment and date. These are different kinds of evidence.

Examples labelled as proposals are integration targets, not existing BDD step
definitions or passing tests. The articles do not infer production readiness
from file presence, a conceptual paper, an exported function or another
component's successful run. In particular, deterministic encoding establishes
repeatable representation; it does not establish the truth of arbitrary input.

* An integration path for operational knowledge

A focused proposed demonstration is a small set of authorised operational
records, one reproducible retrieval question and one explicit relation rule.
Signed events and supporting attachments can then be connected to the same
evidence, with DamageBDD checking the expected result and refusal cases.
Payments and chain commitments should be added with their own settlement
evidence rather than inferred from successful messaging.

The articles identify which parts have code or results today and which still
need integration evidence. Start with the private-retrieval and relation
articles for knowledge work, or the bunker and reliability articles for the
signing handoff.
